# SPC-0003 · Interactive specification workspace

Tier: **feature** · Readiness: **100%**

Builds on: SPC-0001, SPC-0002

A zero-build interactive web workspace that reads the exported graph index to provide at-a-glance health dashboards, derived human/agent task queues, interactive left-to-right lineage visualization, searchable record inspection, and guided record capture.

## Requirements

### REQ-0010 · Workspace dashboard and prioritized task queue surface blockers and next actions (active)

The workspace MUST provide a Dashboard view and a Tasks view driven by the exported index. The Dashboard MUST display a summary callout linking to the task queue (failing closed with an error callout whenever `summary.errors > 0` or global `issues` exist), segmented status bars per record type mapping effective record states to four visual tones (`done`, `wait`, `bad`, `off`—treating active facts strictly past `review_after` as `wait` in both status tones and segmented bars, non-active requirements resting on refuted or deprecated grounds as `broken`, requirements with open questions as `asked`, and requirements resting solely on facts as `ready`), cards for non-active or errored specs with blocker breakdowns, and open questions and assumptions ranked by downstream impact reach. The Tasks view MUST derive a prioritized action queue grouped into five levels (*Fix now* for broken requirements and check errors including global graph errors, *Answer questions* for open questions, *Test assumptions* for open assumptions with validation plans, *Quick wins* for requirements and specs ready to activate, and *Tidy up* for ungrouped requirements and warnings) with direct action links to prefill capture forms or edit records.

**REQ-0010#1**

```gherkin
Given a record index containing an open question and an open assumption
When the dashboard and task queue are computed
Then open questions appear before open assumptions, ranked by downstream reach, and each generates a corresponding action item in the task queue
```

Because:
- FCT-0008 (active): Time-sensitive facts about external environments, tools, and operational limits can become stale
- FCT-0009 (active): Derived action queues and interactive lineage views reduce manual cross-referencing during blocker triage

### REQ-0011 · Interactive lineage graph visualizes upstream grounds and downstream impact (active)

The workspace MUST provide a Graph view that arranges records in five columns from left to right (`ASM`, `FCT`, `QST`, `REQ`, `SPC`) connected by directed curves: solid grounded edges for validated facts and active requirements, dashed weak edges for unvalidated assumptions, open questions, or non-active requirements, and right-gutter loops for spec-to-spec `depends_on` links. Hovering or focusing a node MUST preview its lineage, and clicking a node (or pressing `Enter` in the graph search input) MUST lock selection, elevating active lineage nodes and edges onto a foreground layer while dimming unrelated records, stopping upward traversal at `depends_on` spec boundaries, and displaying upstream/downstream counts, a section excerpt, and dependency jump controls in a sticky status bar. Typing in the graph search input without an active selection MUST dim unrelated records and unrelated edges, keeping only matching records and edges between matching records highlighted. Pressing `Escape` MUST clear the active selection or search filter.

**REQ-0011#1**

```gherkin
Given a feature spec that builds on a skeleton spec and has its own requirements
When the feature spec is selected in the lineage graph
Then upward lineage includes the feature spec's own requirements and grounds plus the skeleton spec node itself, without traversing into the skeleton spec's internal requirements
```

**REQ-0011#2**

```gherkin
Given an unselected graph with a search query entered
When matching records are highlighted
Then unrelated records and unrelated edges are dimmed while matching records and edges between them remain prominent
```

Because:
- FCT-0009 (active): Derived action queues and interactive lineage views reduce manual cross-referencing during blocker triage

### REQ-0012 · Record browser, detail inspection, guided capture forms, and theme persistence (active)

The workspace MUST provide a Records list view supporting filtering by record prefix and effective status plus full-text search across ID, title, and body; a Record detail view rendering the record's Markdown body alongside a metadata sidebar (`Confidence`, `Evidence`, `Review after`, `Tier`, `Readiness`, `Promoted from`, `Promoted to`, `Answered by`, `Blocks`, `Open questions`, `Because`, `Builds on`, `Requirements`, `Used by`, and `Changing this affects`) with links to focus the record in the graph or edit it in version control; a Capture view providing guided forms for all five record types that assigns the next sequential ID (`<PREFIX>-000N`), supports query-parameter prefill (`promote` for assumptions and `answers` for questions), renders a live file preview, and lists companion edits required in the same pull request; and a persistent theme toggle (`System`, `Light`, `Dark`).

**REQ-0012#1**

```gherkin
Given an open assumption or open question selected for promotion or answering in the Capture view
When the form is filled with title, statement, and evidence
Then the preview shows the next sequential fact ID, populates `promoted_from` or companion `answered_by` instructions, and lists every downstream requirement that must be updated in the same change
```

Because:
- FCT-0002 (active): Plain text under version control provides commit attribution, line-level diffs, and reversible history
- FCT-0009 (active): Derived action queues and interactive lineage views reduce manual cross-referencing during blocker triage

## 2. File & Record Conventions (`records/`)

1. **Path & Filename:** Every record is a UTF-8 Markdown file in `records/` named `<ID>-<slug>.md`, where `<ID>` matches `^(ASM|FCT|QST|REQ|SPC)-\d{4}$`.
2. **YAML Front Matter:** Bounded by `---\n...\n---\n` at the top of the file.
   - Common keys: `id` (string), `title` (string), `status` (string).
   - `ASM` keys: `status` in `{"open", "validated", "invalidated"}`, optional `confidence` (float `0..1`), `promoted_to` (`FCT-xxxx`, required when `validated`). Markdown sections: `## Statement`, `## How we validate it`.
   - `FCT` keys: `status` in `{"active", "deprecated"}`, `evidence` (non-empty string, required), optional `promoted_from` (`ASM-xxxx`), optional `review_after` (`YYYY-MM-DD`). Markdown section: `## Statement`.
   - `QST` keys: `status` in `{"open", "answered"}`, `blocks` (non-empty list of `REQ-xxxx` / `SPC-xxxx`), optional `answered_by` (`FCT-xxxx` or `ASM-xxxx`, required when `answered`, forbidden when `open`). Markdown section: `## Question`.
   - `REQ` keys: `status` in `{"provisional", "active", "broken"}`, `because` (non-empty list of `FCT-xxxx` / `ASM-xxxx`). Markdown sections: `## Statement`, `## Acceptance` (one or more scenario blocks separated by blank lines, each line prefixed with `- Given ...`, `- When ...`, `- Then ...`).
   - `SPC` keys: `status` in `{"draft", "active"}`, `tier` in `{"skeleton", "feature"}`, `requirements` (list of `REQ-xxxx`), optional `depends_on` (list of `SPC-xxxx`). Markdown sections: `## Purpose`, optional `## Non-goals`.
3. **Stack-Term Guardrail (`STACK_TERMS`):** Whole-word case-insensitive regex `(?<![\w-])(...)(?![\w-])` scanned across `r.title + "\n" + r.body` (not front-matter `evidence`):
   `postgres`, `postgresql`, `mysql`, `sqlite`, `mongodb`, `redis`, `kafka`, `rabbitmq`, `react`, `vue`, `angular`, `svelte`, `django`, `flask`, `fastapi`, `spring`, `rails`, `node.js`, `nodejs`, `typescript`, `javascript`, `python`, `java`, `golang`, `docker`, `kubernetes`, `aws`, `azure`, `gcp`, `graphql`, `grpc`, `json schema`.

## 3. Module API & CLI Contract (`tools/spec.py`)

### Python Module API (`tools/spec.py`)

- `TYPES = {"ASM": "assumption", "FCT": "fact", "QST": "question", "REQ": "requirement", "SPC": "spec"}`
- `valid_scenario(sc: list[str]) -> bool`: verifies that each scenario step starts with `Given`, `When`, `Then`, `And`, or `But` and includes at least one `Given`, `When`, and `Then` step.
- `class Record(path: Path, meta: dict, body: str)`:
  - Attributes: `self.path`, `self.meta`, `self.body`, `self.id = str(meta.get("id", ""))`, `self.prefix = self.id[:3]`, `self.status = meta.get("status")`, `self.title = meta.get("title", "")`.
  - Methods: `links() -> list[str]`, `section(heading: str) -> str`, `scenarios() -> list[list[str]]` (splits `## Acceptance` on blank lines and strips leading `-`).
- `load(root: Path = RECORDS) -> dict[str, Record]`: loads sorted `*.md` files into a dict keyed by `rec.id` (raising `SystemExit` on missing front matter or duplicate `id`).
- `check(records: dict[str, Record]) -> tuple[list[str], list[str]]`: returns `(errors, warnings)` where each entry is formatted as `"<r.path.name>: <message>"` (or `"spec dependency cycle: a -> b -> a"`).
- `open_questions(r: Record, records: dict[str, Record]) -> list[str]`: returns sorted `QST` IDs with `status == "open"` that list `r.id` in `blocks`.
- `readiness(spec: Record, records: dict[str, Record]) -> int`: returns `round(100 * len(active_reqs) / len(reqs))` or `0` if empty.
- `topo(specs: list[Record], records: dict[str, Record]) -> list[Record]`: orders specs with `skeleton` before `feature` and dependencies before dependents, raising `ValueError("spec dependency cycle: ...")` on cycles.
- `impact(changed: str, records: dict[str, Record]) -> tuple[list[str], list[Record]]`: returns `(sorted_non_spec_ids, ordered_spec_records)` downstream of `changed`.
- `render_markdown(...)`, `render_gherkin(...)`, `render_openspec(...)`, `render_speckit(spec: Record, records: dict[str, Record], stack: str = "") -> str`: all Markdown-family renderers (`markdown`, `openspec`, `speckit`) accept optional `stack` text and append `## Technology Stack` when provided, and all four renderers surface spec-level and requirement-level open questions.
- `to_index(records: dict[str, Record]) -> dict`: dates parsed from front-matter (such as `review_after` parsed by PyYAML as `datetime.date`) are formatted as ISO `YYYY-MM-DD` strings before JSON serialization, and global diagnostics not tied to a single record ID are preserved in top-level `"issues"`.
- `verify_traceability(records: dict[str, Record], code_root: Path) -> tuple[list[str], list[str]]`, and `main(argv: list[str] | None = None) -> int`.

### CLI Subcommands

1. `python tools/spec.py check [--strict] [--verify DIR]`
   - Prints `WARN  <filename>: <message>` for each warning and `ERROR <filename>: <message>` for each error.
   - When `--verify DIR` is passed, scans `DIR` for `REQ-xxxx` / `REQ-xxxx#n` citations, errors on unknown requirement IDs or out-of-range scenario IDs, and warns on uncited active requirements or scenarios.
   - Prints summary line: `<N> records · <E> errors · <W> warnings`.
   - If `errors == 0`, prints each spec in topological order (`skeleton` before `feature`, breaking ties by ID):
     `  <SPC-ID> [<tier:<8>] <readiness:>3}% ready  <title>`
   - Exits with code `1` if `errors > 0` or (`--strict` and `warnings > 0`), else `0`.
2. `python tools/spec.py impact <ID>`
   - Exits with `1` and prints `unknown record <ID>` if `<ID>` is not in `records/`.
   - Otherwise prints:
     ```text
     Changing <ID> affects: <comma-separated sorted non-SPC IDs or 'nothing'>
     Rebuild specs in order: <SPC-ID -> SPC-ID ... or 'none'>
     ```
3. `python tools/spec.py render [--tier skeleton|feature] [--format markdown|gherkin|openspec|speckit] [--stack FILE] [--out DIR]`
   - Default `--format` is `markdown` (`.md`); `gherkin` writes `.feature`, `openspec` writes `.openspec.md`, and `speckit` writes `.speckit.md`. Default `--out` is `dist`.
   - When `--stack FILE` is provided, reads `FILE` (exiting `1` with `unknown stack file <FILE>` if missing) and appends a `## Technology Stack` section to rendered Markdown specs.
   - Writes `<out>/<SPC-ID><ext>` for each matching spec in topological order and prints `wrote <out>/<SPC-ID><ext>`.
4. `python tools/spec.py index [--out FILE]`
   - Default `--out` is `site/data/index.json`.
   - Serializes the JSON object returned by `to_index(records)` with `indent=1, ensure_ascii=False` and prints `wrote <out>`.

### `site/data/index.json` Schema

```json
{
  "repo": "owner/name",
  "summary": { "records": 31, "errors": 0, "warnings": 0 },
  "issues": [],
  "spec_order": ["SPC-0001", "SPC-0002", "SPC-0003"],
  "records": [
    {
      "id": "REQ-0001",
      "title": "...",
      "status": "active",
      "because": ["FCT-0001", "FCT-0002"],
      "type": "requirement",
      "path": "records/REQ-0001-atomic-records.md",
      "body": "## Statement\n...",
      "downstream": ["SPC-0001", "SPC-0002", "SPC-0003"],
      "issues": [],
      "open_questions": []
    }
  ]
}
```
- `repo` is resolved by `github_repo()` from `GITHUB_REPOSITORY` or `git remote get-url origin` (`owner/name`).
- `created_at` and `updated_at` front-matter keys are omitted from `records` entries; any `datetime.date` front-matter values (such as unquoted `review_after`) are converted to ISO `YYYY-MM-DD` strings.
- `REQ` and `SPC` entries carry `"open_questions": [...]`; `SPC` entries additionally carry `"readiness": <0..100>`.
- Any check errors/warnings for a record are attached to its `"issues"` list as `"error: <msg>"` or `"warning: <msg>"` (matching `name[:8]` against `r.id`), while global errors not tied to a single record ID are placed in top-level `"issues"`.

## 4. Web Workspace Architecture (`site/`)

- **`site/index.html`**: Links `https://jvanheerikhuize.github.io/asdlc-meta-designsystem/latest/src/tokens/tokens.css` and `.../latest/src/index.js`, renders `<ui-navbar id="navbar">` with brand link (`#/`), 5 primary navigation links (`Dashboard` `#/`, `Tasks` `#/tasks`, `Graph` `#/graph`, `Records` `#/records`, `Capture` `#/capture/requirement`), `<main id="main" tabindex="-1">`, and footer with `#repo-link`.
- **`site/app.js`**:
  - Fetches `data/index.json` (`cache: "no-cache"`), builds lookup maps (`byId`, `askedBy`, `usedBy`), attaches a badge with total task count to the `Tasks` nav link (`.top-nav a[data-route="tasks"]`), and routes on `location.hash`.
  - Listens to `ui-theme-change` on `#navbar` and persists `"theme"` (`"dark"` | `"light"`) and `"capture:<kind>"` in `localStorage`.
  - Uses `asdlc-meta-designsystem` Web Components (`<ui-stat-tile>`, `<ui-callout>`, `<ui-progress>`, `<ui-badge>`, `<ui-dot>`, `<ui-chip>`, `<ui-input>`, `<ui-textarea>`, `<ui-select>`, `<ui-checkbox>`, `<ui-code-block>`, `<ui-button>`, `<ui-surface>`, `<ui-divider>`, `<detail-layout>`) across the 5 views specified in `SPC-0003` (`dashboard`, `tasksView`, `graph`, `records`/`record`, `capture`).
- **`site/styles.css`**: Maps application aliases (`--bg`, `--surface`, `--text`, `--muted`, `--line`, `--soft`, `--accent`, `--fact`, `--assume`, `--req`, `--spec`, `--question`, `--bad`) directly to `asdlc-meta-designsystem` tokens without redeclaring `--font-*`, `--space-*`, `--radius-*`, or `--shadow-*` on `:root`.
