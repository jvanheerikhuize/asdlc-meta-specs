# SPC-0002 · Rendering and guardrails

Tier: **feature** · Readiness: **100%**

Builds on: SPC-0001

Flesh on the skeleton: mandatory acceptance scenarios, rendering to target formats, a machine-readable index for the workspace, and a guard against technology creeping into the spec. Fully grounded in verified facts.

## Requirements

### REQ-0004 · Every active requirement carries a Given/When/Then scenario (active)

A requirement MUST have at least one Given/When/Then scenario under `## Acceptance` before it can become `active` (failing with `active requirement needs at least one Given/When/Then ...`), and every scenario block in `## Acceptance` MUST consist of steps beginning with `Given `, `When `, `Then `, `And `, or `But ` (case-insensitive) including at least one `Given`, one `When`, and one `Then` step (failing with `malformed acceptance scenario ...`).

**REQ-0004#1**

```gherkin
Given an `active` requirement with no scenario
When the graph is checked
Then the check fails
```

**REQ-0004#2**

```gherkin
Given a requirement whose `## Acceptance` section contains freeform placeholder text lacking `Given`/`When`/`Then` steps
When the graph is checked
Then the check fails and reports a malformed acceptance scenario
```

Because:
- FCT-0005 (active): At least one Given/When/Then scenario per requirement anchors baseline agent implementation and test traceability

### REQ-0005 · Specs render to several target formats from the same records (active)

The system MUST render specs in topological order into each supported target format (`markdown`, `gherkin`, `openspec`, and `speckit`) without editing the records, SHOULD allow filtering by `--tier` (`skeleton` or `feature`), and SHOULD allow binding an external technology stack document at render time (`--stack FILE`) so concrete stack choices are appended to rendered Markdown specs under `## Technology Stack` while keeping `records/` technology-free. Markdown output MUST include the spec ID, title, tier, readiness percentage, optional `Builds on:` list, purpose, optional `## Non-goals` section when declared, spec-level open questions under `## Open questions (do not guess, ask)` as `- <QST-ID>: <title>`, each requirement's ID, title, status, statement, fenced `gherkin` acceptance blocks, `Because:` ground list, requirement-level open questions under `#### Open questions (do not guess, ask)` as `- <QST-ID>: <title>`, and the optional `## Technology Stack` section when `--stack` is supplied. Gherkin `.feature` output MUST emit a `Feature:` header (tagged with `@<QST-ID>` for any spec-level open questions) and one `Scenario: <REQ-ID> <title> #<N>` block per acceptance scenario, tagged with `@provisional` or `@broken` for non-active requirements and `@<QST-ID>` for blocking open questions, and MUST emit a comment preserving `<REQ-ID>`, status, and `@<QST-ID>` tags for any requirement that has no acceptance scenarios yet. OpenSpec output MUST emit `## Purpose`, optional `## Non-goals`, spec-level open questions, `## Requirements` with `### Requirement: <REQ-ID> · <title>`, requirement status and `because` grounds, requirement-level open questions, and `#### Scenario: <REQ-ID>#<N>` blocks with uppercased Gherkin keywords (`- **GIVEN** ...`). Spec Kit output MUST emit `# Feature Specification: <title>`, a spec metadata summary line, purpose, optional `## Non-goals`, `## User Scenarios & Testing` with `**Acceptance Scenario <REQ-ID>#<N>**` blocks, `## Requirements` / `### Functional Requirements` with `- **<REQ-ID>**: <statement> *(grounds: <comma-separated because IDs>)*`, and `## Clarifications` / `### Needs Clarification (do not guess, ask)` when any open question blocks the spec or its requirements.

```gherkin
Given a skeleton spec and a feature spec
When rendering is requested for the skeleton tier only
Then only the skeleton spec is written
```

**REQ-0005#2**

```gherkin
Given a stack-agnostic spec and an external technology stack file
When Markdown rendering is requested with `--stack`
Then the rendered spec includes the `## Technology Stack` section without modifying any record
```

**REQ-0005#3**

```gherkin
Given a spec with a `## Non-goals` section
When Markdown rendering is requested
Then the rendered spec includes the `## Non-goals` section before `## Requirements`
```

**REQ-0005#4**

```gherkin
Given an open question that blocks a requirement
When the spec containing that requirement is rendered
Then the question appears under the requirement
```

Because:
- FCT-0004 (active): Evaluated coding agents ingest Markdown and Gherkin text files directly without intermediate schema compilation
- FCT-0007 (active): Compact renderers project a single record graph into multiple purpose-specific target views

### REQ-0006 · Specs describe behaviour, never technology (active)

Records SHOULD NOT name languages, frameworks, databases or vendors in their `title` or `body`. The check MUST scan each record's `title` and `body` case-insensitively, emit a warning naming the sorted lowercase matched terms (`tech-stack term(s) [...]`) when any are found, and fail in strict mode.

**REQ-0006#1**

```gherkin
Given a requirement that names a specific database product
When the graph is checked in strict mode
Then the check fails and names the lowercase term
```

Because:
- FCT-0006 (active): Externalizing incidental technology choices into a separate binding keeps specification corpora stack-neutral

### REQ-0009 · Export a complete machine-readable index of the record graph for the workspace (active)

The system MUST export a single machine-readable index document containing the repository identifier, summary counts (`records`, `errors`, `warnings`), top-level `issues` for global diagnostics not tied to a single record ID, the topological `spec_order` list, and an entry for each record with its metadata (excluding internal timestamps and normalizing any parsed date values such as `review_after` to ISO `YYYY-MM-DD` strings), full `type` name, relative `path`, trimmed `body`, sorted `downstream` impact list, attached `issues` (`error: ...` and `warning: ...`), `readiness` percentage for specs, and blocking `open_questions` for requirements and specs.

**REQ-0009#1**

```gherkin
Given a valid record graph with specs, requirements, facts, assumptions, and questions

Then the index contains summary counts, topological spec order, downstream impact lists, spec readiness percentages, and per-record issues
```

Because:
- FCT-0007 (active): Compact renderers project a single record graph into multiple purpose-specific target views
- FCT-0009 (active): Derived action queues and interactive lineage views reduce manual cross-referencing during blocker triage

### REQ-0013 · Acceptance scenarios carry sequential IDs and trace to test citations (active)

Rendered Markdown specs MUST label each acceptance scenario with a sequential ID (`**<REQ-ID>#<N>**`). When checking the graph with `--verify DIR`, the system MUST scan source and test files under `DIR` (skipping version-control, dependency, cache, build-output, `records`, and `site` directories) for `REQ-xxxx` or `REQ-xxxx#n` citations, fail on unknown requirement IDs (`<citing-file>: cites unknown requirement <REQ-ID>`) or out-of-range scenario IDs (`<citing-file>: cites unknown scenario <REQ-ID>#<N>`), and warn on any `active` requirement lacking a citation or any numbered scenario lacking a citation when at least one numbered scenario for that requirement is cited without a bare `REQ-xxxx` citation.

**REQ-0013#1**


**REQ-0013#2**

```gherkin

```

Because:
- FCT-0001 (active): Small atomic record corpora check in under 150 ms and avoid file-level conflicts on distinct records
- FCT-0009 (active): Derived action queues and interactive lineage views reduce manual cross-referencing during blocker triage

## 2. File & Record Conventions (`records/`)

1. **Path & Filename:** Every record is a UTF-8 Markdown file in `records/` named `<ID>-<slug>.md`, where `<ID>` matches `^(ASM|FCT|QST|REQ|SPC)-\d{4}$`.
2. **YAML Front Matter:** Bounded by `---\n...\n---\n` at the top of the file.
   - Common keys: `id` (string), `title` (string), `status` (string).
   - `ASM` keys: `status` in `{"open", "validated", "invalidated"}`, optional `confidence` (float `0..1`), `promoted_to` (`FCT-xxxx`, required when `validated`). Markdown sections: `## Statement`, `## How we validate it`.
   - `FCT` keys: `status` in `{"active", "deprecated"}`, `evidence` (non-empty string, required), optional `promoted_from` (`ASM-xxxx`), optional `review_after` (`YYYY-MM-DD`). Markdown section: `## Statement`.
   - `QST` keys: `status` in `{"open", "answered"}`, `blocks` (non-empty list of `REQ-xxxx` / `SPC-xxxx`), optional `answered_by` (`FCT-xxxx` or `ASM-xxxx`, required when `answered`, forbidden when `open`). Markdown section: `## Question`.
   - `REQ` keys: `status` in `{"provisional", "active", "broken"}`, `because` (non-empty list of `FCT-xxxx` / `ASM-xxxx`). Markdown sections: `## Statement`, `## Acceptance` (one or more scenario blocks separated by blank lines, each line prefixed with `- Given ...`, `- When ...`, `- Then ...`).
   - `SPC` keys: `status` in `{"draft", "active"}`, `tier` in `{"skeleton", "feature"}`, `requirements` (list of `REQ-xxxx`), optional `depends_on` (list of `SPC-xxxx`). Markdown sections: `## Purpose`, optional `## Non-goals`.
3. **Stack-Term Guardrail (`STACK_TERMS`):** Whole-word case-insensitive regex `(?<![\w-])(...)(?![\w-])` scanned across `r.title + "\n" + r.body` (not front-matter `evidence`):
   `postgres`, `postgresql`, `mysql`, `sqlite`, `mongodb`, `redis`, `kafka`, `rabbitmq`, `react`, `vue`, `angular`, `svelte`, `django`, `flask`, `fastapi`, `spring`, `rails`, `node.js`, `nodejs`, `typescript`, `javascript`, `python`, `java`, `golang`, `docker`, `kubernetes`, `aws`, `azure`, `gcp`, `graphql`, `grpc`, `json schema`.

## 3. Module API & CLI Contract (`tools/spec.py`)

### Python Module API (`tools/spec.py`)

- `TYPES = {"ASM": "assumption", "FCT": "fact", "QST": "question", "REQ": "requirement", "SPC": "spec"}`
- `valid_scenario(sc: list[str]) -> bool`: verifies that each scenario step starts with `Given`, `When`, `Then`, `And`, or `But` and includes at least one `Given`, `When`, and `Then` step.
- `class Record(path: Path, meta: dict, body: str)`:
  - Attributes: `self.path`, `self.meta`, `self.body`, `self.id = str(meta.get("id", ""))`, `self.prefix = self.id[:3]`, `self.status = meta.get("status")`, `self.title = meta.get("title", "")`.
  - Methods: `links() -> list[str]`, `section(heading: str) -> str`, `scenarios() -> list[list[str]]` (splits `## Acceptance` on blank lines and strips leading `-`).
- `load(root: Path = RECORDS) -> dict[str, Record]`: loads sorted `*.md` files into a dict keyed by `rec.id` (raising `SystemExit` on missing front matter or duplicate `id`).
- `check(records: dict[str, Record]) -> tuple[list[str], list[str]]`: returns `(errors, warnings)` where each entry is formatted as `"<r.path.name>: <message>"` (or `"spec dependency cycle: a -> b -> a"`).
- `open_questions(r: Record, records: dict[str, Record]) -> list[str]`: returns sorted `QST` IDs with `status == "open"` that list `r.id` in `blocks`.
- `readiness(spec: Record, records: dict[str, Record]) -> int`: returns `round(100 * len(active_reqs) / len(reqs))` or `0` if empty.
- `topo(specs: list[Record], records: dict[str, Record]) -> list[Record]`: orders specs with `skeleton` before `feature` and dependencies before dependents, raising `ValueError("spec dependency cycle: ...")` on cycles.
- `impact(changed: str, records: dict[str, Record]) -> tuple[list[str], list[Record]]`: returns `(sorted_non_spec_ids, ordered_spec_records)` downstream of `changed`.
- `render_markdown(...)`, `render_gherkin(...)`, `render_openspec(...)`, `render_speckit(spec: Record, records: dict[str, Record], stack: str = "") -> str`: all Markdown-family renderers (`markdown`, `openspec`, `speckit`) accept optional `stack` text and append `## Technology Stack` when provided, and all four renderers surface spec-level and requirement-level open questions.
- `to_index(records: dict[str, Record]) -> dict`: dates parsed from front-matter (such as `review_after` parsed by PyYAML as `datetime.date`) are formatted as ISO `YYYY-MM-DD` strings before JSON serialization, and global diagnostics not tied to a single record ID are preserved in top-level `"issues"`.
- `verify_traceability(records: dict[str, Record], code_root: Path) -> tuple[list[str], list[str]]`, and `main(argv: list[str] | None = None) -> int`.

### CLI Subcommands

1. `python tools/spec.py check [--strict] [--verify DIR]`
   - Prints `WARN  <filename>: <message>` for each warning and `ERROR <filename>: <message>` for each error.
   - When `--verify DIR` is passed, scans `DIR` for `REQ-xxxx` / `REQ-xxxx#n` citations, errors on unknown requirement IDs or out-of-range scenario IDs, and warns on uncited active requirements or scenarios.
   - Prints summary line: `<N> records · <E> errors · <W> warnings`.
   - If `errors == 0`, prints each spec in topological order (`skeleton` before `feature`, breaking ties by ID):
     `  <SPC-ID> [<tier:<8>] <readiness:>3}% ready  <title>`
   - Exits with code `1` if `errors > 0` or (`--strict` and `warnings > 0`), else `0`.
2. `python tools/spec.py impact <ID>`
   - Exits with `1` and prints `unknown record <ID>` if `<ID>` is not in `records/`.
   - Otherwise prints:
     ```text
     Changing <ID> affects: <comma-separated sorted non-SPC IDs or 'nothing'>
     Rebuild specs in order: <SPC-ID -> SPC-ID ... or 'none'>
     ```
3. `python tools/spec.py render [--tier skeleton|feature] [--format markdown|gherkin|openspec|speckit] [--stack FILE] [--out DIR]`
   - Default `--format` is `markdown` (`.md`); `gherkin` writes `.feature`, `openspec` writes `.openspec.md`, and `speckit` writes `.speckit.md`. Default `--out` is `dist`.
   - When `--stack FILE` is provided, reads `FILE` (exiting `1` with `unknown stack file <FILE>` if missing) and appends a `## Technology Stack` section to rendered Markdown specs.
   - Writes `<out>/<SPC-ID><ext>` for each matching spec in topological order and prints `wrote <out>/<SPC-ID><ext>`.
4. `python tools/spec.py index [--out FILE]`
   - Default `--out` is `site/data/index.json`.
   - Serializes the JSON object returned by `to_index(records)` with `indent=1, ensure_ascii=False` and prints `wrote <out>`.

### `site/data/index.json` Schema

```json
{
  "repo": "owner/name",
  "summary": { "records": 31, "errors": 0, "warnings": 0 },
  "issues": [],
  "spec_order": ["SPC-0001", "SPC-0002", "SPC-0003"],
  "records": [
    {
      "id": "REQ-0001",
      "title": "...",
      "status": "active",
      "because": ["FCT-0001", "FCT-0002"],
      "type": "requirement",
      "path": "records/REQ-0001-atomic-records.md",
      "body": "## Statement\n...",
      "downstream": ["SPC-0001", "SPC-0002", "SPC-0003"],
      "issues": [],
      "open_questions": []
    }
  ]
}
```
- `repo` is resolved by `github_repo()` from `GITHUB_REPOSITORY` or `git remote get-url origin` (`owner/name`).
- `created_at` and `updated_at` front-matter keys are omitted from `records` entries; any `datetime.date` front-matter values (such as unquoted `review_after`) are converted to ISO `YYYY-MM-DD` strings.
- `REQ` and `SPC` entries carry `"open_questions": [...]`; `SPC` entries additionally carry `"readiness": <0..100>`.
- Any check errors/warnings for a record are attached to its `"issues"` list as `"error: <msg>"` or `"warning: <msg>"` (matching `name[:8]` against `r.id`), while global errors not tied to a single record ID are placed in top-level `"issues"`.

## 4. Web Workspace Architecture (`site/`)

- **`site/index.html`**: Links `https://jvanheerikhuize.github.io/asdlc-meta-designsystem/latest/src/tokens/tokens.css` and `.../latest/src/index.js`, renders `<ui-navbar id="navbar">` with brand link (`#/`), 5 primary navigation links (`Dashboard` `#/`, `Tasks` `#/tasks`, `Graph` `#/graph`, `Records` `#/records`, `Capture` `#/capture/requirement`), `<main id="main" tabindex="-1">`, and footer with `#repo-link`.
- **`site/app.js`**:
  - Fetches `data/index.json` (`cache: "no-cache"`), builds lookup maps (`byId`, `askedBy`, `usedBy`), attaches a badge with total task count to the `Tasks` nav link (`.top-nav a[data-route="tasks"]`), and routes on `location.hash`.
  - Listens to `ui-theme-change` on `#navbar` and persists `"theme"` (`"dark"` | `"light"`) and `"capture:<kind>"` in `localStorage`.
  - Uses `asdlc-meta-designsystem` Web Components (`<ui-stat-tile>`, `<ui-callout>`, `<ui-progress>`, `<ui-badge>`, `<ui-dot>`, `<ui-chip>`, `<ui-input>`, `<ui-textarea>`, `<ui-select>`, `<ui-checkbox>`, `<ui-code-block>`, `<ui-button>`, `<detail-layout>`) across the 5 views specified in `SPC-0003` (`dashboard`, `tasksView`, `graph`, `records`/`record`, `capture`).
- **`site/styles.css`**: Maps application aliases (`--bg`, `--surface`, `--text`, `--muted`, `--line`, `--soft`, `--accent`, `--fact`, `--assume`, `--req`, `--spec`, `--question`, `--bad`) directly to `asdlc-meta-designsystem` tokens without redeclaring `--font-*`, `--space-*`, `--radius-*`, or `--shadow-*` on `:root`.
